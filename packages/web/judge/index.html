WHY GRAFT EXISTS

Coding agents write code. Reusing proven code still needs proof.

To reuse a capability across real repositories, someone still has to establish what the existing implementation actually does, whether its evidence is trustworthy, whether it fits the destination, what must change, and whether it still works afterwards. GRAFT turns that into a verifiable engineering process.

GRAFT is not another coding agent. It is an agent-independent reuse and verification layer: the agent can change, while capability knowledge, compatibility reasoning, provenance and verification evidence stay with GRAFT.

HOW GRAFT 0.6 WORKS

What actually works today

Discover & verified harvest → Capability Memory → Capability Genome → Compatibility Atlas & Preview → Blueprint / Laboratory → Transplant / composition → CUF verification → Revision-bound evidence & Assembly Ledger

Find · Capability Memory

GRAFT indexes folders you authorise, shows why it detected a capability, runs the source to verify it, and remembers the verified record locally, bound to its source revision.

Capability Genome

A deterministic representation derived from the capability package: entrypoints, inputs, outputs, dependencies, security properties and the contract that proves it. Its identity hashes behaviour only.

Compatibility Atlas

A local, evidence-bound record of every transplant attempt and outcome. It informs risk notes; it never overrides a compatibility check or a verdict.

Fit · Compatibility Preview

Before anything is written, a destination is COMPATIBLE, ADAPTABLE or INCOMPATIBLE. Incompatible reuse is refused deterministically, and Apply stays disabled.

Blueprint

A deterministic AGENTS.md handoff: the constraints and verification any compatible coding agent must satisfy.

Laboratory

Design an application from banked capabilities with explicit dependencies, conflicts and evidence. COMPOSITION VERIFIED appears only when every capability passes its own contract on one final revision.

Prove · CUF verification

The vendored CUF proof kernel decides each case and the run verdict and computes the proof root. Required behaviour is reported separately from optional witnesses.

Revision-bound evidence

Evidence is CURRENT only at the verified revision. A later commit makes it STALE rather than pretending the old proof still applies; stored proofs stay intact and exportable.

Data Boundary & custody

Before any optional agent operation, data classes and an ALLOW or DENY decision are recorded. Custody keeps metadata and fingerprints, never raw prompts or secrets.
